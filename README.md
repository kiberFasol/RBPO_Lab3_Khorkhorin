# Лабораторная работа 3. Вариант 22 — Распределение мест в общежитии

Проект представляет собой бэкенд-сервис для управления заселением в студенческое общежитие. В третьей лабораторной сервис переведен с in-memory H2 на PostgreSQL с реальным пользователем БД, ограничениями на уровне таблиц и набором бизнес-операций с транзакционной логикой.

## Стек технологий
- Java 17
- Spring Boot 3.2.5 (Spring Web, Spring Data JPA, Validation)
- PostgreSQL 18
- Lombok
- Maven

## Сущности системы
1. **User (`users`)** — студент или сотрудник/админ (имя, почта, роль).
2. **Room (`rooms`)** — комната (номер, вместимость, флаг доступности).
3. **HousingApplication (`housing_applications`)** — заявление на заселение (студент, дата подачи, статус: PENDING/APPROVED/REJECTED/CANCELLED).
4. **ResidenceContract (`residence_contracts`)** — договор найма (заявление, комната, даты заезда/выезда, статус: ACTIVE/TERMINATED/EXPIRED).
5. **RoomTransferRequest (`room_transfer_requests`)** — заявка на переселение (текущий договор, желаемая комната, дата, статус).

## База данных и безопасность
- Настройки подключения вынесены в `.env` (образец в `.env.example`).
- Для сервиса создан отдельный пользователь `dorm_app_user` с паролем `dorm_secure_pass123`. Ему выданы только права на чтение и запись данных (`SELECT`, `INSERT`, `UPDATE`, `DELETE`). Менять структуру таблиц (`CREATE`, `DROP`, `ALTER`) он не может, в Spring Boot включен `ddl-auto=validate`.
- На уровне БД настроены внешние ключи, уникальность номеров комнат и email, а также `CHECK`-констрейнты (вместимость > 0, валидность email, дата выезда не раньше даты въезда).

## Бизнес-операции
Кроме стандартных CRUD-методов, в сервисе реализовано 5 операций (`/api/operations/...`):

1. **Заселение студента (`POST /api/operations/check-in`)**  
   Создает договор найма на основе одобренного заявления. Проверяет, чтобы у студента не было других активных договоров, комната была открыта и в ней оставались свободные места. При заполнении комнаты автоматически ставит ей `isAvailable = false`.

2. **Одобрение переселения (`POST /api/operations/transfers/{id}/approve`)**  
   Переводит студента в новую комнату по ранее поданной заявке. Проверяет наличие свободных мест в целевой комнате. При успешном переводе освобождает место в старой комнате и занимает место в новой.

3. **Досрочное выселение (`POST /api/operations/contracts/{id}/terminate`)**  
   Закрывает активный договор (ставит статус `TERMINATED` и фактическую дату выезда). Автоматически отклоняет все висящие заявки на переселение по этому договору и освобождает место в комнате.

4. **Закрытие истекших договоров (`POST /api/operations/contracts/process-expirations`)**  
   Регламентная операция: находит все активные договоры, у которых срок выезда уже наступил, переводит их в `EXPIRED` и открывает комнаты для нового заселения.

5. **Вывод комнаты на ремонт (`POST /api/operations/rooms/{id}/maintenance`)**  
   Ставит комнате признак недоступности. Если в комнате кто-то живет, операция по умолчанию вернет ошибку (409 Conflict). При флаге `FORCE_TERMINATE_CONTRACTS` (авария/затопление) текущие договоры принудительно завершаются.

## Запуск проекта

1. **Создание базы данных и пользователя**  
   Выполните SQL-скрипт от суперпользователя postgres:
   ```bash
   psql -U postgres -h localhost -p 5432 -f init-db.sql
   ```
   Скрипт создаст базу `dormitory_db`, ограниченного пользователя `dorm_app_user`, таблицы с ограничениями и базовые тестовые данные.

2. **Запуск тестов**
   ```bash
   mvn test
   ```

3. **Запуск приложения**
   ```bash
   mvn spring-boot:run
   ```
   Сервер запустится на `http://localhost:8080`.

4. **Тестирование запросов**  
   В корне проекта лежит файл `postman_collection.json`. Его можно импортировать в Postman — там собраны как CRUD-запросы по всем таблицам, так и сценарии проверки всех 5 бизнес-операций с положительными и ошибочными кейсами.
